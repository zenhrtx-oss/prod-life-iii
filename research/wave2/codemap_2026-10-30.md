Read-only map of the code Wave 2 will touch. Scope (user, 2026-10-30; tracker `../OK_GAME_TRACKER.md:140,153`): core memory (career clock, story log, fame tiers, discography) plus firsts and flex (firsts checklist, auto nameplate title, ribbons, milestone bars), with **one save-format change**.

Paths are relative to `ok_studio/`. `src/RS` = `src/ReplicatedStorage/OK`, `src/SSS` = `src/ServerScriptService/OK`. Every ref was read in the file on 2026-10-30. Anything marked **external** is a Roblox platform fact that the code doesn't check or measure. **Unverified** marks the few points I couldn't settle from the source.

## 1. The save format

### 1.1 DataService today (v4)
- **Header.** `src/SSS/Services/DataService.lua:1-17` covers the session lock, retries, `_newerSchema`, the reward gate and "Schema v4 adds prof.career and prof.walkins".
- **Version.** `M.SchemaVersion = 4` (`:26`).
- **Clock seams.** `M._now` (`:28`) and `M._day` (`:29`, yyyymmdd UTC from `_now`). Tests replace both: t13:35, t41:22, t60:22, t69:82.
- **Store.**
  - `Config.DataStoreName = "OKStudio_v1"` (`src/RS/Config.lua:10`).
  - One key per player: `"u_" .. UserId` (`DataService.lua:40`).
  - Writes go only through `UpdateAsync`: load at `:162-173`, save at `:274-281`.
- **Defaults.**
  - `DEFAULT = { level = 1, xp = 0, visits = 0 }` (`:36`), and `loadUncached` adds `prof.xpLog = {}` (`:151-152`).
  - `detached()` (`:120-125`) builds a throwaway migrated profile that is never saved.
- **Shapes duplicated on purpose.** `newCareer()` (`:69-71`) and `newWalkins()` (`:72`). The comment at `:68` says "Modules/CareerRules.Defaults matches", and `CareerRules.Defaults` is at `src/RS/Modules/CareerRules.lua:17-19`. A new field in `prof.career` has to change both.
- **`M.migrate(prof)`** (`:75-97`) runs on every load (`:200`):
  - `v<1`: `xpLog` (`:77-80`)
  - `v<2`: `cred`, `gear`, `credits`, `credLog` (`:81-87`)
  - `v<3`: `cred *= 10` (`:88`)
  - `v<4`: `career = newCareer()`, `walkins = newWalkins()` (`:89`)
  - After the steps, on every load: a non-table `career` or `walkins` is replaced whole (`:91-92`), `xp` and `cred` are coerced (`:93-94`), and `level` is recomputed from xp (`:95`).
- **`clean(prof)`** (`:99-105`) is what gets saved: every top-level key except those starting with `_`. It is shallow: a nested `_x` field is saved. Nothing else is filtered, so **every top-level field any system puts on the profile is saved**. `Save` sets `updatedAt` (`:268`) and `v = max(stored v, SchemaVersion)` (`:269`, never lowers it), then adds `lock` (`:271`).
- **Load copy.** Every stored key except `lock` is copied onto the default profile (`:190`). Then `visits += 1` (`:201`), once per load (session), not per day.
- **Newer schema.** A stored `v` above `SchemaVersion` loads flagged `_newerSchema`, plays, and is never written (`:193-197`, `:262`, `:135`, `:140`).
- **No store in Studio.** With no DataStore (Studio by default, or an unpublished place), `M.Persistent = false` and nothing is written (`:446-452`). `Config.Data.UseStoreInStudio = false` (`Config.lua:13-15`).
- **Autosave** every `Config.AutosaveSeconds = 120` (`Config.lua:192`; loop at `DataService.lua:462-467`). There is also the lock heartbeat (`:320-333`).

### 1.4 How earlier bumps were done
- **Pattern A: a `migrate` step plus a version bump.**
  - v1 through v4 each added a guarded `if prof.v < N then ...; prof.v = N end` (`DataService.lua:77-89`).
  - v3 changed data once (Money ×10), and the guard makes it idempotent. t13:189-199 proves "70 → 700 once".
  - v4 added two tables, and the repair lines (`:91-92`) handle corrupt values.
- **Pattern B: lazy defaults with no bump.**
  - The Wave 1 design chose "no schema bump; every field defaults when missing" (`specs/2026-10-26-wave1-life-happens-design.md` §5 "Saves", and §9 call 7 "No save-format bump until Wave 2").
  - `walkins.phone` and `walkins.caps` are filled in `WalkIns.state()` (`WalkIns.lua:139-163`, "schema v4 unchanged: this is the one place they are filled in").
  - `Contracts.state` (`:26-33`), `Dailies.state` (`:16-22`), `Tour.state`, `Gear.state` (`:33-37`) and `Funnel.Step` (`:25`) all default their own fields on touch.
- **Tests that pin the version.**
  - t13 is version-agnostic. It reads `DS.SchemaVersion` and builds "newer" as `SchemaVersion + 1` (t13:42, 88, 184, 196, 206, 215-237).
  - **t41 hard-codes v4**: `DS.SchemaVersion == 4` (t41:47), stored `v == 4` (t41:55, 71). Its `sameWalkins` asserts **exactly 4 keys** in a round-tripped `walkins` (t41:61-63), so a v5 `migrate` that injects keys into `prof.walkins` breaks t41(b).
  - t41:48-53 asserts the career defaults, including `careerLog`.

### 1.5 How a v5 bump would work
1. Set `M.SchemaVersion = 5` and add `if prof.v < 5 then prof.<new> = new<New>(); prof.v = 5 end` after `:89`. If it should repair like career and walkins, add a type repair line beside `:91-92`.
2. Put the new data in **a new top-level table**, not inside `prof.career` or `prof.walkins`:
   - `_StudioCareerHook` "Reset" replaces `prof.career` with `Rules.Defaults()` (`Career.lua:203`).
   - `_StudioWalkInHook` "Reset" replaces `prof.walkins` (`WalkIns.lua:746`).
   - t41 pins both shapes (t41:48-53, 61-63).
   - A new table needs its own reset hook so tests can isolate it (see §7).
3. The backfill for an existing v4 profile is a design rule, because no history exists anywhere (see §7.2). The `migrate` step is the place to derive it: tier high-water mark from `career.followers`, firsts from current counts, clock starting at day 1.
4. Update t41:47, 55 and 71, add a v4 → v5 case beside t41(a) (the pattern at t41:43-56), and keep t13's `SchemaVersion + 1` check.
5. Rolling publish (`DataService.lua:193-197`): once any v5 server saves a profile, an old v4 server that loads it plays but doesn't save that session. That is the existing, tested design (t13:213-237), so the cost is only during the publish window.

## 2. What already exists to reuse (and not duplicate)

### 2.1 Credits ("your own credits")
- `prof.credits` is **session-request deliveries only**: `{ t = brief.title, a = artist.name, s = stars, d = yyyymmdd }`. It is written in `Contracts.Deliver` (`Contracts.lua:159-160`, including repeats) and capped at 50.
- The artists are the session artists from `Data/Artists`, not walk-in visitors.
- **Walk-in placements and hits record nothing per artist** (confirmed by research `bitlife_ideas_2026-10-24.md:90`, "walk-in placements write nothing per artist"). `Career.Add` only bumps the counter.
- The date `d` uses `os.date("!%Y%m%d")` on the real clock (`Contracts.lua:159`). That bypasses the `ctx.Data._now` seam every other day computation uses, so a test can't move it.
- **Shown in:**
  - the Credits tab, "Your credits" (`PanelUI.lua:60-74`)
  - the Profile tab, the last 8 (`PanelUI.lua:99-104`)
  - the public card's `credits` count and `recent` 3 (`Profiles.lua:13-18`, `:28`)
  - the credits wall prompt, which opens the Credits tab with the whole profile (`InteractionService.lua:80-82`)
- `Data/Credits.lua` is retired and empty. t06:16 and t50:71 assert it stays empty.
- **Discography implication:** it is a new list keyed by visitor id, beside `credits`, not inside it. `credits` has a different artist roster, its own cap, and the "prod. you" rendering.

**The Wave 1 design's tier lines**: §4.2 (`specs/2026-10-26-wave1-life-happens-design.md:130-146`) says rookie under 1K, booker at 5K, blogger at 10K, famous at 20K, "line up with the fame tiers ... LOCAL 0 · BUZZING 1K · KNOWN 5K · FAMOUS 20K · ICON 100K, so Wave 2's tier names fall on the same lines". §8.2 (`:325-329`) covers the narrow gating of existing cards and "nothing that pays a Placement is gated". The vision page lists what each tier brings (BUZZING: phone pops, a local sponsor; KNOWN: the booker; FAMOUS: the gossip page and the manager; ICON: label deals).

**Off-line gates.** 2K (`hacked`, two NEWS cards) and 10K (`trending`) sit between tiers. Nothing gates at 100K today.

**How the gate works.**
- `WalkInRules.GateOk(card, career, visits)` (`:185-195`): every `needs` value must be met (have ≥ n), and every `under` value must not be reached (have < n).
- Keys are `CAREER_GATES` (`:175-180`: aura, followers, placements, hits, sponsors, money) plus `visits`. An unknown key is never eligible.
- The content validator rejects unknown keys (`spec/walkins_data_spec.lua:34` `GATE_KEYS`, `:296-302`).
- `visits` in the gate is **the walk-in count** (`walkins.count`), set in three `pickOpts`: `WalkIns.lua:305-311`, `Phone.lua:312-322`, `CareerSim.lua:363-370`.
- `Seed` (`:275-289`) gives a newly eligible card the lowest seen count, so a gate opening never causes a burst (design §4.2 "no burst"). `Pick` runs `Seed` first in all three callers (`WalkIns.lua:323`, `Phone.lua:348`, `CareerSim.lua:368`).

**"New people at a tier" with the existing gates.**
- **No rule change is needed.** Tier cards are ordinary cards with `needs = { followers = 5000 }`.
- "Only at that tier" adds `under = { followers = 20000 }` (a band). Today `needs` alone keeps a 5K card in the pool at 20K and 100K.
- Seed already handles the first appearance, and CareerSim already picks them up through the same deck (§5).
- `Data/WalkIns` is pure, with no `require` (`:2-3`). It can't read a `Config.FameTiers` table, so the thresholds must be literal numbers, and a spec should assert that they equal the tier table (the pattern t46 uses for `READY` / `PHONE_CAPS`).
- A stored `tier` gate key would instead mean touching `CAREER_GATES`, `GATE_KEYS`, all three `pickOpts`, and `walkin_rules_spec`. Followers numbers avoid that.
- **Followers fall.** Losses `followers = -200` sit on every artist's bad outcome (e.g. `:160`, `:235`) and `-500` on the phone scam (`:1580`), applied through `Career.Take` (`WalkIns.lua:251`, `Phone.lua:171`). The live value can drop back under a line, so:
  - **The banner and "first time at FAMOUS" need a saved high-water mark.** Otherwise the banner can repeat at 4,999 / 5,000.
  - Content gates on live Followers can close again, which is how gates already behave.
  - The test hook's `Set` bypasses `Changed`, so derive the tier on `Publish` or read rather than only on events.

## 7. Risks

### 7.1 Save size
- The story log and discography grow with every card: up to 8 walk-ins and 6 pops a day (`Config.lua:158`, `:190`).
- A 60-line story log (research `:41`) and a capped discography keep the profile bounded. Store ids, not text (card id, choice index, outcome key, visitor id, day), as research `:41` proposes. The client already has `Data/WalkIns` (it's in ReplicatedStorage) to rebuild text, and names stay roster-switchable.
- No code measures profile size. A size line in a test (for example `#HttpService:JSONEncode(clean(prof))` against a budget) would be new.
- **Payload size**: the whole profile is sent on every OpenPanel and on `ProfileFunction` (§2.5). Serving story, discography and firsts through `Career.State` / `Career_Get` (fetched in the background, `PanelUI.lua:270-285`) avoids that; so does a dedicated remote. Remote payload limits are external.

### 7.2 Old profiles
- **There is no history to backfill.** No days-played counter (README M12), no per-artist placements (§2.1), no first dates, no tier history.
- A v4 profile with `placements = 3, hits = 1, followers = 25000` arrives at v5 with nothing behind those numbers. Design rules are needed:
  - the clock starts at day 1 (or is seeded from `visits`, which counts sessions)
  - firsts already true are marked earned with no date
  - the tier high-water mark is set from current Followers **without** a banner
  - the discography starts empty, or with "earlier work" lines derived from counts
- `level` is always recomputed from xp (`DataService.lua:95`). Anything keyed to level needs no migration.
- Studio play never persists (`UseStoreInStudio = false`), so no real profile has been saved through Studio. The published place's live store is the only source of real old profiles (README:162).

### 7.3 Replication of new attributes
- Player attributes (`Level`, `Aura`, `Followers`, ...) replicate to every client. That's how the server-built nameplate and other players' clients read them.
- New `Year`, `Title` or `Tier` attributes would follow `Career.Publish` (`Career.lua:77-87`) and `DataService.setAttrs` (`:46-58`). Both run on join (`Career.lua:236-238`) and after every Add or Take.
- Nameplate listeners are an explicit list (`Nameplate.lua:40`), and HUD listeners are explicit too (`HUD.lua:283-300`). New attributes must be added there.
- Attributes hold only primitive types: a ribbon list would need a joined string, like `CareerGates` (`Career.lua:86`) and `Gear` (`Gear.lua:85`).
- A **midnight rollover** for online players (the clock) needs a loop like `Dailies.lua:130-140`. Reading `ctx.Data._day()` keeps it testable; the Contracts date (`:159`) is the one place that bypasses the seam.

### 7.4 The Studio-only fake store
- t13, t41, t60 and t69 use `DS._SetStoreForTest(fake)` (`DataService.lua:435-440`). Each one's `UpdateAsync` stores **the Lua table by reference** (`t13_check.lua:28-32`, `t41_check.lua:15`, `t60_check.lua:15`, `t69_check.lua:76`).
- It never JSON-encodes, so it won't catch values a real DataStore rejects or reshapes: sparse arrays, numeric keys, mixed tables, NaN, Instances, Color3.
- The codebase already guards against this with string keys: `funnel[tostring(n)]` (`Funnel.lua:26-27`), `fireLog.given[tostring(authorId)]` (`Reactions.lua:46`, `:83`), `daw.slots.s1` (`DAW.lua:157-158`), and BeatBus's note (`BeatBus.lua:3`).
- Story and discography should be dense arrays of small records, and per-artist maps keyed by visitor id strings.
- With `UseStoreInStudio = false`, `Save` returns `"nostore"` in every Play test (`DataService.lua:264`). **The v5 round-trip can only be proven in edit-mode checks** like t41(a/b). Play tests only see the in-memory profile.

### 7.5 Smaller risks
- **Copy**:
  - t50 bans "STUDIO TWO". Use `g.name` "THE HALL" (`Config.lua:139`).
  - t40 bans "Cred".
  - Names must come from the roster.
  - The research examples' "YEAR 7 · HITMAKER" collides with rank HITMAKER (`Config.lua:93`); research `:180` notes the title list must be disjoint from the ranks or replace them.
- **HUD layout**:
  - The space under the pills is taken: the BUSY DAY chip (`HUD.lua:123-125`, `:143-145`), the float chains (`:50-54`, `:226-256`), the Daily pill (`ClientMain.client.lua:99-104`, x 12, y 66, 312 wide), the tour card, the cypher bar, the phone icon and FIRE's column (`HUD.lua:5-9`).
  - All of this is checked by t45b and t62. Milestone bars on the HUD are the riskiest piece; the Career-tab tiles (`PanelUI.lua:206-222`) are the safe home.
- **Banner collision**: `bannerToken` (`HUD.lua:268-276`); a tier crossing often lands with the same card that levels you.
- **System init order**: `SystemLoader` starts systems in `GetChildren()` order (`SystemLoader.lua:10`). New systems should require others lazily, as WalkIns and Phone do with Funnel.
- **`Career.Changed`** is a BindableEvent. Handlers run outside the `apply` pcall, so they can't break a card. They also can't see the card. Signal ordering under deferred signal behaviour is **unverified** here (a workspace setting not visible from `src/`).
- **`careerLog` naming** (§2.9) and the `first` flag (§2.9).

## Design implications

1. **One v5 step, one new top-level table** (for example `prof.life` / `prof.story`, not inside `career` or `walkins`), with a reset hook. Bump `SchemaVersion` to 5, add the `migrate` step after `DataService.lua:89`, and update t41:47/55/71. Keep `prof.walkins` at 4 keys for t41(b).
2. **The career clock needs its own saved fields** (last played day as yyyymmdd and a day count), stepped on load and by a midnight loop (`Dailies.lua:130-140` pattern), read through `ctx.Data._day()`. Don't reuse `walkins.day`, `daily.day` or `visits`.
3. **Fame tiers are a Config table plus a saved high-water mark.** Detect crossings in a `Career.Changed` listener *and* on Publish (the hook `Set` bypasses events). Banner only on a new high. Content gates stay as literal Followers numbers in `needs`/`under`, with a spec asserting they equal the tier lines. No new gate key.
4. **Discography and story log record at the `WalkIns.apply` / `Phone.deliver` call sites**, which know the card and visitor. Hits at `onArrive` (`WalkIns.lua:436-447`), placements at `Choose` → `apply`, the two-sessions payoff at `onArrive`. Store ids, cap the lists (50/52 precedents), and render names on the client from `Data/WalkIns` + roster.
5. **Serve memory through `Career.State` / `Career_Get`**, not the profile payload that every OpenPanel ships. Put the story, firsts and bars in the Career tab, not a sixth tab or the HUD. Name new rows so they don't start with `Gate_` or `CareerGear_`.
6. **Firsts mirror `Funnel.Step`'s once-ever pattern** (string keys, saved). If any pays, it needs a `Config.Career.Sources` entry *and* a CareerSim mirror, and must keep the 200-seed floor (≥ 0.3412; about 0.017 headroom). Cosmetic firsts cost the economy nothing.
7. **Nameplate title and YEAR**: new attributes plus listeners at `Nameplate.lua:40`; update t22's exact strings. Pick title words disjoint from `Config.Ranks` (HITMAKER, STUDIO LEGEND), or decide to replace ranks (t21:20). Watch the 220×48 plate math in `WalkIns.lua:222-225` and `Visitor.lua:173`.
8. **Card fields**: every addition to `Profiles.PUBLIC` changes t25's exact count of 17 and t41(g).
9. **Banner**: reuse `OK_LevelUp`, but queue banners instead of letting `bannerToken` drop one. Keep the geometry t68 pins. A new sound changes t11's 17 and needs t14.
10. **Backfill rules for v4 profiles are a user decision**: clock start, firsts already earned without dates, tier set silently, empty or derived discography.
11. **Tier-gated new cards go through the existing deck and sim automatically**, but they dilute walk-in money. Use the §8.1 levers (caps, the phone) and add a Followers/tier-day output to `CareerSim.Run` so the design can state when players reach each tier.
